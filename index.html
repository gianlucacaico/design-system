Imagery

No stock photos

Three kinds of image, all drawn in the system's own colours, glass and type. Each one shows real content from where it sits, never decoration.

Post artwork

One illustration per post, used three ways: the banner under the title, the thumbnail in post lists and the featured card, and the image people see when the post is shared.

  1. Keep what matters in the middle 80%. The featured card trims the sides.
  2. Keep the bottom-left corner clear. The Featured label sits there.
  3. Draw the post's actual idea. Ink background, colour fields, glass panels and Inter, using only words, figures and labels from the post.
  4. Check it small. It has to read as a thumbnail as well as a banner.

Project pictograms

Each project's key artefact, drawn for the right side of its card at full height and cropped by the card's edges. The eye goes from the client's name, to the pictogram's focal point, to the labels, with no frame or tile around it. The tints are under Colour, in Artwork.

  1. Name corner stays clear: x under 60, y under 48. Check any name longer than "Generation Life" at phone width.
  2. Label corner stays clear: x under 110, y over 112.
  3. One focal point, fully inside. Draw big and let context run off the right, top or bottom edge, fading in from the left. A half-cut icon reads as a mistake.
  4. White, then one tint. White for main shapes, white at 20 to 45% for secondary ones, and exactly one tint for the insight, picked to contrast with the card.
  5. No words or figures. Only what the card itself already says.

Client names

Project cards write the client's name as text, top left, rather than showing its logo. A logo needs the client's formal permission, so the written name is the default.

  • Name as text. 18px, bold and white, top left of the card's art, clear of the pictogram.
  • Logos only with formal permission. If a client ever gives it: use the brand's own white version, never recoloured, stretched or redrawn, about 18 to 32px high, with the name as alt text.

Governance

How it stays true

A design system is only useful while it matches what ships. These are the rules for keeping it in step with gianlucacaico.com, and for changing either one safely.

Who owns what

gianlucacaico.com
The source. Pages, components and artwork are designed and shipped there first.
This design system
The standard. The tokens, components and rules, written down so any page can use them.
Gianluca
Approves every change before it goes live, on either site.
Claude sessions
Draft changes, preview them, open a review page, and check the live site after publishing.

How a change goes live

  • Nothing goes live without approval, and approval for one change doesn't carry over to the next.
  • One change per review page, with the current and proposed wording side by side and phone and desktop previews.
  • Check the live site after publishing, not just the code.
  • Every change can be undone by reverting its review page on GitHub.

The drift check

The kit is a copy of the site's styles, so a check compares the two and says when they part ways. It runs from both sides, each reading what the other publishes: this design system reads the site's live stylesheet at the end of every preview, and the site reads this design system's tokens in its health check after every publish. Either side can also run it on a change before it merges.

Compares
Every colour, card art and layout token on the site with the kit, plus the colours in the site's artwork template and pictograms.
Drift
A token differs, or exists on only one side. Fix it before publishing, by updating the kit or asking whether the site is right.
Info
A colour is used but isn't a token yet. That's a to-do list for the kit, not a blocker.

Versions

  • Version 1 only gets changes that can't break a page: new tokens, new components, fixes, and values that follow the site's look.
  • A breaking change becomes version 2, at its own address, and only with Gianluca's approval. Version 1 then stays as it was.
  • The unversioned kit is always the latest. Only this site's own pages rely on it.

Proposing a change

  1. Start on the main site if it changes how something looks. The design system follows.
  2. Name new colours and sizes as tokens, each with a plain-English use.
  3. Match the site's class names for new components, and add each one to the demo with placeholder copy.
  4. Run the preview. It has to pass with no drift.
  5. Open a review page and record any design decision in the log below.
